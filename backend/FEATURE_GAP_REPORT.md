# 功能缺口报告 — 实际工作层面

> 生成日期：2026-03-20
> 基于对后端代码库的全面分析，从实际运营角度评估的功能缺口，按优先级排列。

---

## 一、高优先级 — 核心运营缺口

### 1. 通知推送系统（完全缺失）

当前系统没有任何主动通知机制。以下场景在实际工作中会严重依赖通知，但目前完全依赖用户主动刷新：

- 任务被分配给志愿者 → 无推送
- 案件状态变更（找到人了）→ 家属无通知
- 任务临近截止 → 无提醒
- 管理员发布紧急寻人 → 附近志愿者无推送

**需要实现**：微信订阅消息（小程序端）+ 短信通知（重要事件）+ 站内消息表。

---

### 2. 地理位置功能（仅存储，无能力）

代码中有 `latitude/longitude` 字段，但：

- 没有"附近案件"查询（志愿者看不到周围有哪些案件需要处理）
- 没有"附近志愿者"召集（发布紧急任务时无法通知附近的人）
- 轨迹记录有写入，但没有轨迹可视化数据接口（地图渲染需要按时间序列返回所有坐标点）
- 没有按行政区划（省/市/区）的统计分组

实际寻人工作高度依赖地理信息。

---

### 3. 人员信息匹配（完全缺失）

系统能录入走失人员信息，但：

- 没有相似案件匹配（同一人可能被多次上报，或被不同地方发现）
- 没有特征检索（按年龄范围、体貌特征、失踪地区的复合查询）
- 没有"疑似发现"关联机制（志愿者在A市发现一名流浪老人，系统无法自动关联B市的走失案件）

这是寻亲系统的核心业务价值所在。

---

### 4. 志愿者能力与状态管理（缺失）

当前任务分配是管理者手工指定，但没有：

- 志愿者专长标签（擅长水上搜救、有车、会方言等）
- 志愿者当前状态（可用/执行中/暂停）
- 服务时长统计（志愿者考核、荣誉体系的基础数据）
- 资质认证状态（是否通过培训、是否实名认证）

没有这些，任务分配只能靠人工经验，规模扩大后无法管理。

---

## 二、中优先级 — 影响工作效率

### 5. 数据导出与报告生成

实际工作需要向政府、媒体、家属提交报告，但系统没有：

- 案件详情 PDF 导出（含照片、轨迹、处理历史）
- 月度/年度统计报表导出（Excel）
- 志愿者服务记录证明（个人服务时长、参与案件数）
- 寻人信息海报生成（带二维码的标准格式图片，可直接转发）

---

### 6. 家属端独立入口（缺失）

当前系统所有用户都在同一角色体系内。实际需要：

- 家属能自助上报案件（无需注册为机构用户）
- 家属能查看自己案件的进展（但不能看其他案件的内部信息）
- 家属能补充新线索（上传新照片、更新特征描述）
- 有人找到线索时家属能第一时间收到通知

目前家属和志愿者使用同一入口，权限设计无法区分。

---

### 7. 紧急广播机制（缺失）

儿童走失的黄金 6 小时内，需要：

- 向特定地理范围内的所有用户推送紧急通知
- 设置紧急等级触发自动扩散（案件标记 `critical` 后自动通知附近用户）
- 支持跨组织的紧急协作请求

当前 `urgency` 字段存在但只是标记，没有触发任何行为。

---

### 8. 操作记录不完整

审计日志记录了 API 调用，但缺少业务级的案件时间线：

- 案件从创建到关闭的完整操作流水（谁在什么时间做了什么，附备注）
- 轨迹记录者信息（当前只存坐标，不记录是哪个志愿者在现场添加的）
- 任务完成时的工作记录（完成报告、现场照片、处理说明）

---

## 三、低优先级 — 完善性功能

### 9. 批量操作

- 批量分配任务（一次性把多个任务分给不同志愿者）
- 批量更新案件状态（月末结案清理）
- 批量导入历史案件数据

### 10. 线索管理模块（缺失）

当前任务是"做什么"，但"发现了什么"没有独立管理：

- 线索录入（目击者信息、发现地点照片）
- 线索可信度评级
- 线索与案件的关联追踪
- 匿名线索提交（知情人不愿暴露身份）

### 11. 对外集成接口

- 公安系统数据对接（走失人员信息共享）
- 社交媒体一键转发接口（微博/朋友圈）
- 其他公益组织的 API 数据共享

### 12. 短信通知触达（已有 SMS 但未用于业务事件）

SMS 服务目前只用于登录验证码。实际需要在以下业务事件中触达用户：

- 任务分配通知（可能没有开微信）
- 案件关键进展（家属随时知道）
- 逾期任务催办（志愿者未按时完成）

---

## 优先级汇总

| 优先级 | 功能 | 理由 |
|--------|------|------|
| P0 | 通知推送（微信订阅消息 + 业务短信） | 无通知则信息流断裂，系统无法驱动工作 |
| P0 | 人员特征匹配与相似案件检测 | 核心业务价值，避免重复上报、漏找 |
| P1 | 地理位置查询（附近案件/志愿者） | 寻人工作强地理依赖 |
| P1 | 家属独立入口与线索补充 | 家属是最重要的信息来源 |
| P1 | 案件 PDF / 寻人海报导出 | 线下工作必须 |
| P2 | 志愿者能力标签与状态管理 | 规模化后必需 |
| P2 | 紧急广播机制 | 儿童失踪黄金时间窗口 |
| P2 | 业务级案件时间线 | 法律/存档合规 |
| P3 | 线索管理模块 | 完善证据链 |
| P3 | 批量操作 | 效率提升 |
| P3 | 对外集成接口 | 生态扩展 |

---

## 核心结论

当前系统是一个完整的 CRUD 管理平台，但还不是一个能驱动实际寻人工作流转的系统。最关键的两个缺口是**通知推送**（信息流通）和**地理+特征匹配**（核心搜索能力）。没有这两项，系统只能作为台账工具，无法成为协作工具。
